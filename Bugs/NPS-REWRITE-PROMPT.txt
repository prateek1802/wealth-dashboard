PART 2 — THE REAL ARCHITECTURE: NPS is units × NAV per scheme, not a lump sum
====================================================================
Verified against a real multi-year NSDL/Protean statement (Tier I, PRAN-linked, HDFC
Pension Fund, Life Cycle 50 — Moderate auto-choice, Dec 2022 through Jul 2026).

WHAT THE CURRENT SCHEMA GETS WRONG:
nps_accounts.current_corpus is a single manually-maintained number. Real NPS isn't that
— it's 3 (or 4, if Scheme A/Alternative Assets is used) separate sub-funds, each with its
own unit balance and its own daily NAV, same concept as mutual fund units. A subscriber's
real corpus is `sum(units_held_per_scheme × latest_NAV_per_scheme)`.

REQUIRED SCHEMA CHANGES (supabase/schema.sql AND sync-schema.sql — both need updating,
sync-schema.sql must stay idempotent per its existing convention):

  create table nps_scheme_holdings (
    id uuid primary key default gen_random_uuid(),
    user_id uuid not null default auth.uid() references auth.users(id) on delete cascade,
    nps_account_id uuid not null references nps_accounts(id) on delete cascade,
    scheme text not null check (scheme in ('E', 'C', 'G', 'A')), -- Equity / Corp Bonds / Govt Securities / Alternative
    units_held numeric(18,4) not null default 0,
    last_nav numeric(12,4),
    last_nav_date date,
    created_at timestamptz not null default now(),
    updated_at timestamptz not null default now(),
    unique (nps_account_id, scheme)
  );

  create table nps_scheme_transactions (
    id uuid primary key default gen_random_uuid(),
    user_id uuid not null default auth.uid() references auth.users(id) on delete cascade,
    nps_account_id uuid not null references nps_accounts(id) on delete cascade,
    scheme text not null check (scheme in ('E', 'C', 'G', 'A')),
    transaction_date date not null,
    transaction_type text not null check (transaction_type in
      ('contribution', 'switch_in', 'switch_out', 'fee', 'withdrawal')),
    -- NOTE: no 'nav_framework_credit' type needed — that event is a 1:1 reissuance
    -- of existing units under a new NAV basis, not a real transaction. It should be
    -- SKIPPED entirely by the import parser (see Part 4), never stored as a row.
    amount numeric(18,4) not null,       -- signed: positive for contribution/switch_in, negative for switch_out/fee/withdrawal
    nav numeric(12,4) not null,
    units numeric(18,4) not null,        -- signed, same convention as amount
    employee_amount numeric(18,4),       -- only meaningful for transaction_type='contribution'; null otherwise
    employer_amount numeric(18,4),       -- only meaningful for transaction_type='contribution'; null otherwise
    linked_transaction_id uuid references nps_scheme_transactions(id), -- pairs a switch_out with its switch_in
    description text,                    -- raw description from the statement, kept for reference/debugging
    created_at timestamptz not null default now()
  );
  create index nps_scheme_transactions_account_date_idx
    on nps_scheme_transactions (nps_account_id, transaction_date);

MIGRATION FOR EXISTING DATA: existing nps_accounts.current_corpus rows and the existing
nps_contributions table should NOT be dropped — keep nps_contributions as-is (it's still
useful as a simple combined-amount log for accounts where the user doesn't want to do
full scheme-level tracking). Instead:
  - current_corpus on nps_accounts becomes a DERIVED/computed value going forward
    (sum of units_held × last_nav across that account's nps_scheme_holdings), not a
    column the app writes to directly anymore. Keep the column for backward
    compatibility / accounts that haven't been migrated to scheme-level tracking yet,
    but the service layer should prefer computing from nps_scheme_holdings when
    holdings exist for that account, falling back to the stored current_corpus
    otherwise. This lets a user who imports a real statement get real derived values,
    while someone who's just manually tracking a lump sum still works as before.

PART 3 — TRANSACTION CLASSIFICATION RULES (validated against real multi-year data —
follow these exactly, they were checked against actual totals that matched to the rupee)
====================================================================
When importing or manually logging, classify by description text:

  "contribution" / "arrear" (e.g. "By Contribution for <Month><Year>", "By Arrear - DA
  ARREARS", "By Arrear - PAY DIFFERENCE") → transaction_type = 'contribution'.
    - These are the ONLY rows that count toward "total invested."
    - IMPORTANT CAVEAT discovered during validation: in a scheme-wise statement, the
      "Amount" column per scheme is that scheme's SHARE of the combined
      employee+employer contribution for that month (split per the account's asset
      allocation), NOT an employee-only amount. If your source data doesn't separately
      break out employee vs employer per scheme, leave employee_amount/employer_amount
      null on the scheme_transactions row and instead capture the split (when
      available) once at the account level, e.g. from the "Contribution/Redemption
      Details" section of a CRA statement, which DOES report employee vs employer
      separately (unscoped to any one scheme).

  "switch in" / "switch out" (e.g. "By Switch In From <PFM> SCHEME <X> ... On account of
  Rebalancing of Assets as per Regulatory Requirement") → transaction_type =
  'switch_in' / 'switch_out'.
    - These are paired: a switch_out from scheme A and a switch_in to scheme B on the
      SAME DATE with the SAME rupee amount (unit counts differ because NAVs differ
      between schemes). Link them via linked_transaction_id when importing.
    - CRITICAL: switches must NEVER count toward "total invested" and must NEVER be
      treated as XIRR cash flows. No new money enters or leaves the NPS account — it's
      the PFM moving existing money between its own sub-funds. This happens
      automatically, roughly yearly, for any lifecycle/auto-choice account as the
      subscriber ages. Validated: summed across all schemes in a real multi-year
      account, switch amounts net to ~₹0 (small residual is just per-scheme NAV
      rounding, not a real gain/loss).

  "billing" (e.g. "Billing for Q4 2022-2023") → transaction_type = 'fee'.
    - Small negative amount, small negative units. This is a PFM/CRA administrative
      fee. Excluded from "total invested." Should count as a (tiny) negative XIRR cash
      flow if you want full accuracy, though its impact is negligible in practice.

  "credit of units due to implementation of multiple nav framework" (or similarly-named
  one-off regulatory/technical events — this exact wording is what appeared in real
  data from a framework change PFRDA rolled out; there may be other one-off event types
  like this in the future, treat any unrecognized large one-time "credit" with the same
  suspicion) → DO NOT CREATE A ROW AT ALL. SKIP.
    - VALIDATED FINDING: in real data, this row's unit count was found to be EXACTLY
      equal (to 4 decimal places, across every scheme) to the running unit total that
      already existed immediately before that row. It is a 1:1 reissuance of the
      subscriber's existing holding under a new NAV/unit basis — not new units, not new
      money. If you naively add it to the running unit total (as a first pass
      incorrectly did during scoping this feature), you will roughly DOUBLE the
      computed corpus. The fix that was validated to produce the correct total: skip
      the row entirely — don't add its units, don't add its amount anywhere. If a
      future statement shows something like this again with a different label, apply
      the same check before trusting it: compare the row's unit count against the
      running total immediately prior. If they match (or the row is otherwise
      unreasonably large relative to normal monthly contribution size), treat it as a
      reissuance/restatement event and skip it, don't add it as a transaction or as
      invested capital.

  "opening balance" / "closing balance" → informational only, not a transaction. Can be
  used to sanity-check the running total after import, but don't insert as a row.

  "withdrawal" (not seen in the sample data used for validation, since NPS Tier I
  withdrawals are rare pre-retirement — but the existing withdraw() function in
  nps.repository.ts already handles simple corpus-reduction withdrawals) — for
  scheme-level tracking, a real withdrawal would need units removed from one or more
  specific schemes at that day's NAV. Model this as transaction_type = 'withdrawal'
  with negative amount/units on the affected scheme(s). Keep the existing simple
  npsRepository.withdraw() path working for accounts that aren't using scheme-level
  tracking.

VALIDATION CHECK TO BUILD INTO THE IMPORT PARSER: after classifying all rows for an
account, sum(contribution amounts) should be checkable against any "Total Contribution"
figure the source statement itself reports (CRA statements usually include this in an
"Investment Summary" section) — surface a warning if they don't match within a small
tolerance, since that's a strong signal a row was misclassified.

PART 4 — IMPORT: parse real NSDL/Protean statement formats
====================================================================
Two real formats were seen and should both be supported:

FORMAT A — single-period CRA CSV export ("NPS Transaction Statement for Tier I
Account"). Has a header section (PRAN, subscriber name, scheme choice), an "Investment
Summary" section with an official reported XIRR (useful for validating your own XIRR
calc against — treat mismatches beyond a small tolerance as worth surfacing to the
user, not silently swallowing), a "Scheme Wise Summary" table, a "Contribution/
Redemption Details" table (has the employee/employer split at the whole-account level),
and then per-scheme "Transaction Details" tables with Date/Description/Amount/NAV/Units
columns.

FORMAT B — consolidated multi-year export, one workbook/sheet per scheme (columns:
Date, Description, Amount (in Rs), NAV, Units — no header/summary sections, just the
raw transaction log per scheme). This is the denser, more useful format for a full
history import since it's not bounded to one statement period.

Build the parser to detect which format it's looking at (sheet/column structure differs)
and handle both. For Format B (multi-sheet workbook), use the SheetJS (xlsx) library
already available in this project's stack for spreadsheet parsing — same library already
used elsewhere in the app's ecosystem for reading Excel. For Format A (CSV with mixed
header+table sections), a straightforward line-by-line parse that looks for the "Date,
Description, Amount (in Rs), NAV, Units" header row to know where each scheme's
transaction table starts/ends is enough — it doesn't need a general CSV table detector,
just recognition of that specific recurring header row per scheme block.

Follow the docx/pptx/xlsx skill guidance already in this environment for how to read
xlsx files if writing this as a one-off analysis; for the actual in-app import feature
this becomes a proper parser module (e.g. src/lib/import/nps-statement-parser.ts) that
the transactions/import feature can call, similar in spirit to the existing CSV
import-csv-dialog.tsx pattern already used for regular securities transactions —
consider whether the import UI should live alongside NPS (nps-view.tsx) or reuse/extend
the existing import dialog component.

PART 8 — ONGOING DATA ENTRY: periodic full-statement re-upload (idempotent import)
====================================================================
Manually logging every NPS contribution one-by-one doesn't scale. The user has
decided: periodic re-upload of the full consolidated statement is the whole
solution here — no quick-entry/provisional-data fallback needed. Keep this simple.

FLOW: the user periodically re-downloads their full consolidated statement from
NSDL/Protean (same multi-sheet xlsx or CSV format Part 4's parser already handles —
no new format needed) and re-uploads it through the same import feature built in
Part 4. Since most rows will already exist from a previous import, the import MUST
BE IDEMPOTENT:

  - Dedup key: (nps_account_id, scheme, transaction_date, description, units).
    Units are precise to 4 decimal places, so combined with the other three fields
    this is effectively collision-free for genuinely distinct transactions.
  - On import: for each parsed row, check whether a row already exists matching the
    dedup key. If yes, skip it (don't insert, don't update). If no, insert it.
  - After import, show a summary: "X new rows imported, Y already existed and were
    skipped" — so the user gets confirmation the re-upload did something (or
    didn't, if nothing's changed since the last upload).
  - No new UI beyond what Part 4's import feature already needs — same upload
    dialog, same parser, just invoked again later with a newer export. The "Log
    contribution" manual-entry dialog in nps-view.tsx can stay as-is for anyone who
    prefers it, but re-upload is now the primary/recommended path — consider
    updating the empty-state / help text on the NPS page to point users toward
    "Import statement" rather than manual logging as the first thing they try.

Write a test for the dedup logic specifically: import the same file twice in a row
and assert the second import inserts zero new rows. This is the one behavior this
whole feature depends on being correct — get it covered before considering Part 8
done.
