🆕 NEW BUG, found while diagnosing Analytics page complaints: Volatility/Sharpe/
   Sortino were showing implausible values (>500). Root cause: these are computed
   from variance of period-to-period snapshot returns. With only ~8 snapshots
   required, a single bad data point dominates. This project's NPS corpus
   calculation genuinely changed methodology multiple times (corpus-doubling bug
   fixed, contribution-sync bug fixed, later switch to derived units×NAV corpus) —
   if even one historical snapshot was recorded mid-transition, it shows an
   artificial 30-50%+ net worth swing that was never a real market move, and that
   one point is enough to blow these metrics into the hundreds. This is the SAME
   root cause as the CAGR methodology-mixing issue above, but hits these three
   metrics much harder since they're sensitive to every step of the path, not just
   endpoints. Fix fully spec'd in ANALYTICS-REDESIGN-PROMPT.txt (Part II) —
   cutoff-date filtering plus outlier-return exclusion, with a test using a
   deliberately-planted extreme snapshot.

CONTEXT

Continue work on the wealth-dashboard project. Workflow: single git patch file per

The current Analytics page (src/app/(app)/analytics/page.tsx) is a flat stat-dump —
11 numbers in boxes (CAGR, XIRR, Realized/Unrealized P&L, Volatility, Max Drawdown,
Sharpe, Sortino, Concentration %) plus one donut and a forward-looking growth

REAL BUG ALREADY DIAGNOSED, FIX THIS FIRST: Volatility/Sharpe/Sortino are computed
from variance of period-to-period snapshot returns (risk.ts). With only ~8 snapshots
required, a single bad data point dominates the whole calculation. This project's
NPS corpus calculation changed methodology multiple times over its history (a
corpus-doubling bug that got fixed, a contribution-sync bug that got fixed, a later
switch to derived units×NAV corpus) — if even one historical snapshot was recorded
mid-transition between these, it shows an artificial 30-50%+ net worth swing that
was never a real market move, and that single point is enough to blow these three
metrics into the hundreds. FIX: add a configurable cutoff (e.g. an env var or a
constant with today's date as a starting placeholder the user can adjust) so
risk.ts's calculateVolatility/calculateSharpeRatio/calculateSortinoRatio only
consider snapshots ON OR AFTER that cutoff — treat anything before it as
methodology-contaminated, not real portfolio history. Also add basic outlier
protection as a second layer of defense: if any single period-to-period return
exceeds a sanity threshold (e.g. ±30% in one gap — implausible for a real diversified
portfolio's actual day-to-day move), exclude that one return from the variance
calculation rather than let it dominate, regardless of what caused it. Write a test
using a fixture with one deliberately extreme outlier snapshot mixed into otherwise
normal ones, asserting the outlier gets excluded and the resulting Sharpe/Sortino/
Volatility stay in plausible ranges (Sharpe/Sortino roughly -5 to 5, Volatility
roughly 0-150%).

SHORT ANSWER: Mostly yes at the database layer (indexes, RLS, batched fetches within
a single function are all done correctly), but there's one clear, fixable inefficiency
at the service layer — the same base data gets fetched from the database multiple
times per page load — plus a couple of smaller frontend opportunities. Nothing here
is "broken" or user-visibly slow yet at your current data volume, but the dashboard
redundancy is worth fixing before transaction/holding counts grow much further.

====================================================================
✅ GENUINELY WELL OPTIMIZED
====================================================================

1. Database indexes are thorough and well-targeted.
   18 indexes total. Every single RLS-filtered user_id column has its own index
   (critical — RLS applies a WHERE user_id = auth.uid() to every query, so without
   these indexes every query would silently degrade to a full table scan as data
   grows). Plus sensible composite indexes matching actual query patterns:
   transactions (asset_id, transaction_date), price_history (asset_id, recorded_date),
   nps_contributions (nps_account_id, contribution_date). This is genuinely
   well-designed, not just "indexes exist."

2. computeHoldings() itself is correctly batched, not N+1.
   Fetches assets and transactions in one Promise.all (2 queries total), then filters
   in JS — this is the right pattern. The problem (see below) isn't this function
   itself, it's that multiple OTHER functions each call it independently instead of
   sharing one result.

3. Price refresh avoids bursting external rate-limited APIs.
   Sequential (not parallel) fetches against Yahoo/CoinGecko/mfapi.in, with per-asset
   failure isolation. Slower per-refresh, but correctly prioritizes not getting
   rate-limited/IP-banned by a free API over raw speed. Reasonable trade-off for how
   this is actually used (manually triggered, not high-frequency).

4. Server Components used correctly for initial data fetching.
   All 15 page.tsx files are async Server Components fetching data server-side before
   render (not client-side useEffect fetching, which would mean an extra
   loading-spinner round-trip on every navigation). This is the correct Next.js
   pattern and it's followed consistently.

====================================================================
🔴 THE MAIN FINDING: redundant data fetching on the Dashboard
====================================================================
dashboard/page.tsx fetches 10 things via one outer Promise.all — good instinct
(parallel, not sequential). But several of those 10 independently re-fetch the SAME
underlying tables instead of sharing one result:

   getPortfolioSummary()      -> computeHoldings() -> assets.findAll() + transactions.findAll()
   getAssetAllocation()       -> computeHoldings() -> assets.findAll() + transactions.findAll()  [duplicate]
   getTopHoldings(5)          -> computeHoldings() -> assets.findAll() + transactions.findAll()  [duplicate]
   getSegregatedBreakdown()   -> computeHoldings() -> assets.findAll() + transactions.findAll()  [duplicate]
   getRecentActivity(6)       -> assets.findAll() + transactions.findRecent()                    [duplicate assets fetch]
   transactionsRepository.findAll()  <- called directly again in the same Promise.all              [duplicate]

Net effect: one Dashboard page load fires assets.findAll() 5 times and
transactions.findAll() (or equivalent) 5 times. Because they're all inside one outer
Promise.all, these execute CONCURRENTLY, not one-after-another — so this isn't
multiplying your page load TIME the way a truly sequential N+1 would (Supabase
handles concurrent requests fine at this scale), but it is:
  - 10 real round-trips to Supabase instead of 2, for data that doesn't change
    between those calls within the same request
  - Real, unnecessary data transfer — the full assets and transactions tables get
    serialized and sent over the wire 5 times each, not once
  - A cost/scale concern more than a current-latency concern: this gets meaningfully
    worse as your transaction count grows (267+ already, per an earlier screenshot),
    and worse again if Supabase billing is ever usage-metered on read volume

FIX: refactor portfolioService so the individual functions (getAssetAllocation,
getTopHoldings, getSegregatedBreakdown, getPortfolioSummary) accept an already-computed
Holding[] as a parameter instead of each calling computeHoldings() internally. Add one
new exported function — e.g. getDashboardData() — that fetches assets+transactions
ONCE, computes holdings ONCE, and derives all the individual pieces (summary,
allocation, top holdings, breakdown) from that single shared result. dashboard/page.tsx
then calls this one function instead of 4-5 separate portfolioService methods. Other
pages (Portfolio, Analytics) that only need one or two of these can keep calling the
individual functions as-is — this fix specifically targets the case where MULTIPLE
derived views are needed in the same request, which today only really happens on the
Dashboard.

====================================================================
🟡 SMALLER OPPORTUNITIES
====================================================================

5. recharts is not code-split.
   No next/dynamic usage found anywhere in the app. recharts (used in
   allocation-donut.tsx, sparkline.tsx, performance-line-chart.tsx,
   nps-projection-chart.tsx) is a genuinely heavy library, and it's currently bundled
   directly into whatever client component imports it — shipped in the initial JS
   bundle for every page that includes a chart, rather than lazy-loaded only when
   that chart actually needs to render.
   FIX: wrap chart components in next/dynamic(() => import(...), { ssr: false })
   (charts need browser APIs anyway, so ssr:false is appropriate, not a compromise).
   Straightforward, low-risk change, meaningfully reduces initial JS payload on pages
   with charts (Dashboard, Analytics, NPS).

6. No memoization in the two largest table components.
   transactions-view.tsx (up to 267+ rows currently) and portfolio-view.tsx do
   grouping/sorting work with zero useMemo. At current data volume this is very
   unlikely to cause any noticeable jank — a few hundred rows of array grouping is
   fast even unmemoized — but worth knowing as a "if it ever starts to feel slow, this
   is the first place to look" note rather than something to fix preemptively right
   now. Low priority.

====================================================================
✅ CHECKED, NOT AN ISSUE
====================================================================

- No literal N+1 query loops found anywhere (i.e. no `for (const x of items) { await db.query(...) }`
  pattern issuing one DB call per row). The redundancy above is duplicate BULK fetches,
  not per-row queries — a meaningfully different (and less severe) category of problem.
- revalidatePath usage in Server Actions looked appropriately scoped, not blanket
  revalidating the whole app on every mutation.

BOTTOM LINE
====================================================================
Nothing here is currently causing a noticeably slow app — Supabase and Next.js are both
forgiving enough at your current data volume (a few hundred transactions, a personal
single-user app) that none of this shows up as a real symptom yet. But #4 (the
Dashboard's redundant fetching) is worth fixing sooner rather than later specifically
because it compounds with data growth over time, which — given this is a long-term
wealth tracker you'll keep adding years of transactions to — is exactly the trajectory

PRIORITY: #4 (dashboard redundant fetch) first — real and growing. #5 (chart

WEALTH DASHBOARD — FEATURE IDEAS FROM LEADING WEALTH APPS
Researched: Empower (Personal Capital), Kubera, Monarch Money, Copilot Money, Quicken
Simplifi, and India-specific apps (INDmoney, Kuvera, Agni Folio) — Aug 2026.
Each idea below is mapped to what it would actually take in THIS app's stack
(Next.js + Supabase, single-user, mostly manual entry + some live price refresh).

====================================================================
🟢 REALISTIC — fits the current architecture, no new infra needed
====================================================================

1. Asset allocation drift / rebalancing alerts (Kuvera, Empower)
   Kuvera flags underperforming holdings against stated targets; Empower shows
   allocation vs. a target model. You already compute allocation % per holding and
   per asset-class group (ASSET_TYPE_GROUP). Add: a user-set target allocation per
   class (e.g. "70% Equity / 20% Debt / 10% Cash"), compare against actual, and
   surface a "you're 8% overweight Equity" banner on the dashboard.

2. Portfolio benchmarking against an index (Kubera: vs. S&P 500/Bitcoin; most apps: vs. Nifty)
   Kubera reports IRR per asset and benchmarks it against a chosen ticker/index. You
   already compute XIRR per holding and portfolio-wide. Add: fetch Nifty 50 / Sensex
   historical values (same live-provider pattern already used for Yahoo/CoinGecko) and
   show "Your portfolio: +14.2% XIRR vs. Nifty 50: +11.8%" alongside existing XIRR cards.

3. Recurring/subscription-style SIP reminder & tracking (most budgeting apps track
   recurring bills; adapted here for SIPs)
   You already have Maturity/reminder bell for FD/PPF/NPS/goals. Extend the same
   mechanism: let a mutual fund holding be flagged as "active SIP" with a day-of-month,
   and the bell reminds if that month's SIP transaction hasn't been logged yet by, say,
   the 5th of the month — catches missed/forgotten manual SIP entries, which matters a
   lot in a manual-entry app like this one.

4. "What changed" summary / weekly recap (Monarch's Weekly Recap, AI-powered Insights)
   Monarch auto-summarizes net worth/cash flow changes in plain language. A
   non-AI version fits easily here: a simple rules-based summary card — "Net worth up
   ₹42,000 this week, driven by SBI Contra Fund (+₹18,000) and NIFTYIETF (+₹9,000)" —
   computed straight from existing snapshot + holdings data, no LLM needed. Could later
   be upgraded to a real AI summary via the Anthropic API if desired.

5. Tax-loss / tax-gain harvesting flags (Kuvera's standout feature)
   Kuvera automatically flags underperforming direct-plan holdings for tax-loss
   harvesting. You already track cost basis and unrealized P&L per lot (FIFO). Add: a
   view that surfaces holdings with unrealized losses eligible to offset short/long-term
   gains elsewhere in the portfolio, with the relevant Indian STCG/LTCG holding-period
   rules (1 year for equity) already computable from existing lot dates.

6. Family / household multi-portfolio view (Kuvera, Kubera's sharing/collaboration)
   Kuvera supports family account management under one dashboard; Kubera has granular
   sharing. Given Supabase RLS is already per-user_id, this is a schema-level feature:
   add a "household" or "linked accounts" concept so someone can view (read-only)
   a spouse/parent's portfolio for a combined net-worth number — without merging the
   actual account data.

7. Physical/alternative asset tracking — gold, property, vehicles (Kubera's breadth;
   very relevant in India specifically — physical gold is a huge asset class here)
   Kubera tracks real estate, vehicles, precious metals, collectibles as manually-entered
   line items alongside synced accounts. Your schema already supports an "other" asset
   type loosely — this would formalize it: dedicated asset types for Physical Gold
   (with weight + purity), Real Estate (with a manual value + optional appreciation
   assumption), similar to how FD/PPF/NPS already get their own dedicated schema/UI
   rather than being crammed into the generic securities table.

8. Insurance & document vault (Safebox's differentiator vs. INDmoney/Kuvera —
   explicitly built for exactly the gap those "investor-first" apps have)
   A simple new feature area: policy name, type, premium due date, sum assured, renewal
   reminder (reuses the existing maturity/reminder bell pattern) — doesn't require
   actual document storage/encryption to start, just tracking dates and amounts.

9. Cash flow forecast (Quicken Simplifi's "Spending Plan" — forward-looking, not
   backward-looking)
   You already have XIRR-based growth projections. A simpler, more immediately useful
   version: project next month's contributions based on the "active SIP" data from #3,
   forecast known FD/PPF maturities in the next N months from existing maturity data —
   giving a "here's what's coming due/contributing in the next 90 days" view, purely
   computed from data you already store.

🟡 REALISTIC BUT NEEDS NEW INFRASTRUCTURE (cron, external APIs, or storage)
====================================================================

10. Automated bank/broker account sync via Account Aggregator framework (INDmoney,

    This is the single biggest capability gap vs. every competitor researched — all of

13. Scenario / "Fast Forward" planner (Kubera's unique feature — project net worth N

    You already have growth-projection.tsx doing XIRR-based projections. Extending it

🔵 WORTH KNOWING ABOUT, BUT LOW FIT FOR THIS APP'S PURPOSE

14. Full budgeting / category-level expense tracking (Monarch, Copilot, YNAB, Simplifi's

    All of the global leaders researched are budgeting-first apps with investment

16. Estate planning / legacy handoff / beneficiary notification (Kubera's "inactivity

APPENDIX 7 — NPS-DETAILED-ENDPOINT-PROMPT.txt (verbatim)
------------------------------------------------------------------------------------
PROMPT FOR NEW CHAT — NPS LIVE NAV: SWITCH TO DETAILED ENDPOINT + STALENESS WARNING
(paste this along with PROJECT-STATUS.md and the source zip, per usual workflow)

====================================================================
CONTEXT — why this matters, confirmed with a real incident
====================================================================
Workflow: single git patch file, verified with tsc/eslint/vitest/next build.

src/lib/market-data/live-provider.ts's fetchNPSNAVQuote() currently uses npsnav.in's
"Simple" endpoint (/api/{scheme_code}), which returns ONLY a bare NAV number — no
date. The function stamps the result with `asOf: new Date().toISOString()` (the
moment the APP fetched it), not the NAV's real publication date.

THIS JUST CAUSED A REAL, MULTI-DAY DEBUGGING SESSION: npsnav.in's own data was
stuck/stale for over 2 days (confirmed directly on their site — their own banner
read "NAV updated: 24-08-2026" while checks were happening on the 26th-27th). The
app kept showing "as of [today]" the entire time, because that timestamp was always
just "when I refreshed," never the true NAV date — completely masking a real
upstream data problem that would have been obvious immediately if the UI showed the
NAV's actual date instead.

====================================================================
THE FIX
====================================================================
1. Switch fetchNPSNAVQuote() to npsnav.in's "Detailed" endpoint instead of the
   Simple one — confirm the exact path and response shape from their docs
   (npsnav.in/nps-api) before wiring it in, since this wasn't independently
   re-verified this session; last confirmed detail was that a detailed variant
   exists and returns a genuine "Last Updated" field alongside the NAV, but the
   exact JSON key names need checking against their current docs directly.

2. Parse and store the REAL last-updated date from that response — this replaces
   the current asOf: new Date().toISOString() fabrication entirely. Update
   nps_scheme_holdings.last_nav_date (already exists in schema) to store this real
   date, not the fetch timestamp.

3. STALENESS WARNING in the UI: on the NPS page, if a connected scheme's
   last_nav_date is more than ~2 calendar days older than today, show a visible
   warning state instead of the normal "Live NAV ... as of [date]" — e.g. a
   yellow/amber treatment with something like "NAV data may be stale — last updated
   [date], source hasn't synced since." This is the single most valuable part of
   this fix: it would have caught the exact 2-day-stale incident automatically,
   the first time it happened, instead of requiring extensive manual
   cross-referencing against the Protean app and npsnav.in's raw site to even
   realize something was wrong.

4. Apply the same staleness check to refreshLiveNAVs()'s result summary — if a
   fetch succeeds (HTTP 200, valid number) but returns a last-updated date that's
   already stale, the toast/summary should distinguish "updated, but source data is
   old" from a genuine fresh update, rather than reporting both as equally
   successful.

====================================================================
WHAT NOT TO CHANGE
====================================================================
- Keep fetchNPSNAVQuote()'s existing fail-soft behavior (return null on any error,
  never throw) — this fix is about the SUCCESS path returning better information,
  not about changing error handling.
- Keep the existing "never auto-guess PFM-to-scheme mapping" design entirely as-is
  — this fix is orthogonal to that.

====================================================================
TEST TO ADD
====================================================================
A test asserting: given a mocked Detailed-endpoint response with a last-updated
date more than 2 days old, the staleness warning condition evaluates true; given a
response from today or yesterday, it evaluates false. Use real boundary cases (2
days ago exactly, 3 days ago) so the threshold behavior is explicit and tested, not
just implied by the code.
